# 0004. 校验失败分流，硬性缺口剔除分母，诊断/校验共享要求清单

状态：已定稿
日期：2026-09-16

## 背景

校验失败有两种本质不同的原因：措辞/结构/格式问题（可修复，该重试）与
JD 要求的事实源里根本没有（不可修复——不能编造）。后者若进重试循环，
改写器被持续施压，压力下的 LLM 最容易擦边编造。另外诊断和校验若各用
一套标准，两套标准会打架。

## 决定

1. 失败分流：可修复 → 带反馈重写（≤2 轮）；硬性缺口 → 不进重试，
   升级回诊断报告（"该岗位要求 X，经历库中没有，建议补充经历或接受
   低覆盖"）。
2. **硬性缺口从校验分母剔除**：改写开始前先对事实源做举证预检，
   注定无证据的条目标记为缺口，改写器目标函数排除它们。不可达条目
   留在分母里 = 覆盖率永远过不去 = 制造擦边压力。
3. 预检偏保守：宁可错标缺口（用户可低成本纠正），不可错判可达
   （擦边压力回归）。缺口条目携带"最接近的经历"，报告呈现为
   "无直接证据，最接近 X，是否相关？"，用户一句话确认即可捞回分母。
4. JD 诊断产物（结构化要求清单：req_id / must|preferred / 关键词 /
   所需证据）**单一来源**，诊断与校验共享，标准不打架。
5. must 与 preferred 缺口分层呈现；全 must 缺口时报告直接提示
   "这个岗位可能不值得投"。

## 后果

- 正面：重试循环有终止保证；擦边编造的结构性诱因被移除；诊断报告
  有超出简历优化本身的决策价值。
- 负面：诊断产物 schema 成为跨模块契约，改动牵连 diagnose、rewrite、
  validate 三方。
- 不可逆性：要求清单 schema 是全链路契约，定型后难改。
