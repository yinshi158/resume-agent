# 简历优化 Agent 架构设计 v0.4（定稿）

内部设计文档，已定稿。记录三轮讨论 + 一轮已知问题评审（《已知问题.md》9 条）后的架构决策。
不可逆决策的正式记录见项目根目录 ard/；后续变更须先改 ard 再改本文档。

## v0.4 变更：已知问题决策

### P0（M1 阻塞）：source_span 锚定层定死——规范原文层（canonical_text）

ingest 产出的**唯一锚定载体是规范原文层**：一份入库即不可变的纯文本，
所有 span / quote / 高亮联动都以它的字符偏移为准。

- Markdown 只是喂给 LLM 的输入视图，**不承载锚点**（格式字符会让偏移漂移）。
- canonical_text 只做**机械归一化**（NFKC、全角→半角、空白折叠）——无损、可逆、
  无歧义。**先归一化再算偏移**。职责是保真 + 锚定稳定。
- **日期归一化不在此层**。日期解释是语义判断（"03/04" 是 3 月 4 日还是 2003 年
  4 月？），会错，不能烤进锚定层。它下沉到抽取层：归一化结果存结构化字段，
  歧义日期走 anomaly 的"日期格式歧义"标记，gate1 呈现为
  "原始日期 ↔ 归一化结果 + 歧义徽标"，人工确认。
  分层原则：锚定层永远保真；解释层允许错、可标记、可确认。
- 双栏/乱序：以抽取器阅读序为准（pymupdf 排序模式；复杂版式切 MinerU）。
  canonical_text 即唯一事实，gate1 左栏直接渲染它，不回链 PDF 视觉坐标；
  v1 不做手动重排交互，但留逃生门：gate1 提供"切换 MinerU 重新解析"入口，
  阅读序混乱时一键重解析，避免"可见不可修"只能改 PDF 重传的死路。

### P1（M2 阻塞）：quote 归一化

归一化只有一个实现，入库和校验共用。校验时 quote 先过同一个归一化函数
再做子串判定，从源头消灭全角/半角/空白误报。

### P2（M3 阻塞）：formula 安全求值

禁用 eval。白名单 AST 求值（Python `ast`，只允许数字、四则运算、括号、
百分号字面量），其余节点类型一律拒绝；区间形式两个端点分别求值。

### P2：中文动词词表列为持续维护资产

归因动词检查依赖"主导级/参与级"两级中文动词词表，版本化管理，
作为独立模块资产 verb_lexicon 写进模块表。

### M3 同步项：gate2 确认行为落库

gate2 上线同时建 gate_events 表（句子 ID、动作 confirm/reject/edit、
编辑前后文本、**当次校验判定快照**、时间戳；validate 结果按句子 ID 持久化
可关联）。分析价值在"校验判定 × 用户行为"配对：用户驳回被 L2 标红的句子 =
误报信号，用户手改未被标红的 = 漏报信号；只有动作没有当时判定，误报率算不出。
这是免费的人工标注数据，价值高于投递回流，错过就从第一天开始丢。

### v2 登记：双模板导出

export 模块登记 v2 事项：网申版（机器解析优先）与直聘版（HR 肉眼阅读，
可适度排版）双模板；v1 只做 ATS 友好单模板。

### v0.3 三个小问题的修复

1. **M1 措辞**：M1 是"不依赖 LLM **调优**"，不是不依赖 LLM——解析本身靠
   LLM 抽 schema。mock 模式的规则抽取对中文简历质量差，演示不得以 mock
   效果充当真实水平。
2. **进度态设计**：诊断页与导出页为分钟级 LLM 任务，必须有分步状态
   （SSE：解析中→举证中→改写第 n 轮→校验中→渲染中），随 M2/M3 交付。
3. **标注测试集进里程碑**：列为 M2 开工条件——10–20 份标好的
   "JD-简历对 + 期望举证结果"，没有它 M2 prompt 无法验收、M3 阈值无从调。

## v0.3 变更：面向国内求职市场 + 第一版做网页

### 国内市场的本土化取舍

- **解析**：中文简历版式复杂（双栏、表格、照片位），pymupdf4llm/markitdown 为主，
  MinerU 作复杂排版兜底（重依赖，按需启用）；扫描件兜底用多模态模型。
- **ATS 规则库**：目标从 Workday 系换成国内实际链路——北森/Moka/大易等 ATS +
  Boss 直聘/智联/猎聘的在线简历解析。规则库 v1 只收确定项：标准章节名、
  单栏、无表格文本框、倒序时间、关键词中英文并写（如"搜索引擎优化（SEO）"）。
- **关键词与校验**：分词不依赖 jieba 等传统分词做判定——quote/span 子串校验
  本身语言无关；关键词覆盖率用"词表 + 别名表"做确定性匹配，中英文别名并表。
- **中文特有处理**：模糊量化词（"近翻倍/约两倍/百余"）走区间映射规则；
  中文日期格式（"2020.3-至今"）在抽取层归一化（不进 canonical_text，见 v0.4 P0）；
  中文简历常见字段（年龄/照片/政治面貌）在诊断报告里给出去留建议，不做强制。
- **模型选型**：LiteLLM 网关，默认 DeepSeek（性价比）,可切 GLM/Kimi/Claude。JD 来源 v1 为用户粘贴文本，不做招聘网站抓取。
- **输入消毒双向**：简历端 + JD 端（粘贴的 JD 同样是不可信输入）。

### 网页版形态

- 单体本地 Web 应用：FastAPI 后端 + **React + Vite 前端**（已拍板，一步到位，
  不做原生 JS 过渡），localhost 运行、单用户、无鉴权。
- 中间产物（事实源、诊断报告、举证表）从文件改为 SQLite 存储，同时保留
  一键导出 JSON 便于调试。
- 两个人工节点即两个核心页面：
  - **gate1 事实源校对页**：左栏原文（span 高亮联动），右栏字段表 + 异象徽标 +
    attribution 确认控件；首次全量模式 / 增量只看标记模式。
  - **gate2 diff 确认页**（M3）：改写前后逐句对照，出处 ID 可点击跳原文。
- LLM key 在设置页配置（OpenAI 兼容端点 + key），无 key 时整个 pipeline
  可用 mock 模式跑通（用规则抽取 + 假改写），保证开发演示不被 key 卡住。

### 里程碑重排

- **M1**（范围已确认，只做这三步，不含任何改写能力）：上传简历 → 解析入库 →
  gate1 校对页（原文 span 高亮联动、异象徽标、attribution 确认）。
  不依赖 LLM **调优**（但解析本身依赖 LLM 抽 schema；mock 模式仅供开发跑通，
  中文简历抽取质量不代表真实水平）。含 canonical_text 规范化层，是地基。
- **M2**：粘贴 JD → 诊断报告页（要求清单、逐条举证 quote、缺口 + 最近经历、
  must/preferred 分层、不值得投提示）+ SSE 分步进度。
  **开工条件：10–20 份标注测试集（JD-简历对 + 期望举证结果）就绪。**
- **M3**：改写 + 三层校验 + 失败分流 + gate2 diff 确认 + PDF 导出 +
  SSE 分步进度。**同步交付：gate_events 表（确认/拒绝/编辑事件落库）、
  verb_lexicon 动词词表、formula 白名单求值器。**

## 贯穿原则

**所有 LLM 输出必须携带可被程序验证的锚点**（source_span / quote / 出处 ID / formula）。
LLM 负责生成，程序负责验证，人工只看程序验证不了或验证失败的部分。

## Pipeline

```
解析入库 → 【人工节点1：事实源校对】→ JD 诊断（结构化）
        → 硬性缺口预检（偏保守）→ 改写（声明出处）
        → 校验（举证式 + 三层幻觉检测）
        → 失败分流 ─┬─ 可修复 → 带反馈重写（≤2 轮）
                   └─ 硬性缺口 → 升级回诊断报告
        → 【人工节点2：diff 确认】→ 导出
```

## 模块拆解

| 模块         | 职责                                   | 关键机制                               |
| ---------- | ------------------------------------ | ---------------------------------- |
| ingest     | 简历解析（PDF/DOCX → 规范原文层 + Markdown 视图 → 结构化 JSON） | 文本层清洗（防注入，含白色隐形文本）；归一化生成 canonical_text（唯一锚定层）；LLM 输出 schema |
| normalize  | 机械归一化函数（NFKC、全半角、空白折叠；**不含日期**）    | 唯一实现，入库与 quote 校验共用。全系统最承重函数：M1 配属性测试（幂等性、中文样本偏移稳定性快照）；实现版本化，任何改动 = 全量重入库 |
| fact_store | 事实源存储与版本管理                           | 每字段带 source_span（锚 canonical_text）；程序验证 span 能定位回原文 |
| anomaly    | 异象信号计算（替代 LLM 自评置信度）                 | 日期倒序/重叠、**日期格式歧义**、百分比超界、金额量级突变、schema 缺字段 |
| gate1      | 人工节点 1：事实源校对                         | 首次全量过；增量只展示异象标记字段；attribution 强制确认；歧义日期"原始↔归一化"对照确认；"切换 MinerU 重新解析"逃生门 |
| diagnose   | JD 诊断：要求清单 + 逐条举证                    | quote 经 normalize 后程序验证子串；缺口带"最接近经历"；SSE 分步进度 |
| rewrite    | 改写器                                  | 目标函数剔除硬性缺口；逐句声明出处 ID；衍生数字带 formula |
| validate   | 校验器组（L0/L1/L2 + 归因动词检查）              | 与 diagnose 共享同一份要求清单；formula 白名单 AST 求值，禁用 eval |
| verb_lexicon | 中文动词词表资产（主导级/参与级，版本化）             | 归因动词检查的唯一依据，持续维护                  |
| gate2      | 人工节点 2：diff 逐条确认                     | 硬性缺口不在此标红；确认/拒绝/编辑事件写入 gate_events |
| export     | ATS 友好模板导出 PDF（v2：网申版/直聘版双模板）       | Playwright 渲染 HTML；SSE 渲染进度       |
| ledger     | 版本—投递—结果三张表 + gate_events 事件表（只记录不分析） |                                    |

## 核心 Schema 草案

### 事实源条目

```jsonc
{
  "id": "exp_001",
  "raw_quote": "负责推荐系统重构，DAU 从 70 万提升到 91 万",  // canonical_text 逐字片段
  "source_span": [1420, 1448],        // canonical_text 字符偏移，程序可回查
  "section": "work_experience",
  "attribution": "individual | team | mixed | unknown",  // 四值
  "attribution_confirmed": false,      // team/mixed/unknown 须人工确认为 true
  "entities": {
    "numbers": [{"value": 700000, "unit": "DAU"}, {"value": 910000, "unit": "DAU"}],
    "orgs": [], "skills": ["推荐系统"]
  },
  "anomaly_flags": []                  // anomaly 模块输出
}
```

### JD 诊断要求清单（diagnose 与 validate 共享）

```jsonc
{
  "requirements": [{
    "req_id": "r1",
    "priority": "must | preferred",
    "text": "3 年以上推荐系统经验",
    "keywords": ["推荐系统"],
    "evidence": {
      "status": "direct | nearest | gap",
      "quote": "负责推荐系统重构……",     // 必须逐字，程序验证
      "fact_id": "exp_001",
      "nearest_fact_id": null             // gap 时携带最接近条目
    }
  }]
}
```

预检偏保守：找不到可验证 quote 一律标 gap（错标缺口用户可一句话捞回，
错判可达则改写器擦边压力回归）。全 must 缺口 → 报告直接提示岗位可能不值得投。

### 改写输出（逐句带锚点）

```jsonc
{
  "sentences": [{
    "text": "主导推荐系统重构，DAU 提升 30%",
    "source_fact_ids": ["exp_001"],
    "derived_numbers": [{
      "value": "30%",
      "formula": "(910000-700000)/700000",   // 允许区间形式
      "source_ids": ["exp_001"]
    }],
    "verbs": ["主导"]                          // 供归因动词检查
  }]
}
```

衍生数字规则：校验器重算 formula，反推值须在原文精度内成立。
模糊量化词（"近翻倍"）：不得引入原文没有的，除非映射到区间且原文数值落区间内。

## 校验分层

- **L0 确定性实体比对**：数字/公司名/技能词正则+词表抽取，改写稿实体 ⊆ 事实源实体 ∪ 合法衍生。
- **归因动词检查（确定性，先于 L2）**：attribution=team/mixed/unknown 的条目不得搭配
  "主导/独立负责"等第一人称主导动词；未确认前只许"参与"级动词。默认值站保守一侧，夸大比谦虚危险。
- **L1 衍生数字校验**：重算 formula，含区间形式。
- **L2 LLM 蕴含判定**：只核对"声明的出处是否蕴含这句话"（借壳加料），
  输出 句子→条目 ID 映射，映射不上标红。

失败分流：可修复（措辞/结构/格式）→ 带反馈重写 ≤2 轮；硬性缺口（分母已剔除，
不再进入重试）→ 升级回诊断报告。

## 评估与防坑

- 诊断与校验共用同一套人工标注测试集（10–20 份 JD-简历对，M2 开工条件）。
- 多版本选优用成对比较，A/B 顺序互换各跑一次，两次一致才采纳；不做绝对打分。
- 注入防御双向：简历端与 JD 端都做输入消毒。
- LLM 节点统一走 LiteLLM；改写用低温；embedding 仅作库变大后的粗排预留，
  当前量级（几十上百条）全量喂，不做检索。

## 技术栈

Python + FastAPI 后端 + React/Vite 前端（本地 Web，见 v0.3）；markitdown/pymupdf4llm 解析，
中文复杂排版上 MinerU；LangGraph 编排重试循环；LiteLLM 多模型网关（默认 DeepSeek，
可切 GLM/Kimi/Claude）；SQLite 存事实源与版本—投递—结果三张表；
Playwright 出 PDF。
