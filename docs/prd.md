# PRD：简历优化 Agent

版本：v1.0（对应架构 v0.4 定稿）
日期：2026-09-16
关联文档：[架构设计](resume-agent-architecture.md)、[ard/](../ard/README.md)、[已知问题](../已知问题.md)

## 1. 产品一句话

面向国内求职者的本地网页应用：把你的真实经历建成一份可信的"事实源"，
针对每个 JD 生成可解释的诊断和**不编造**的定制简历——所有 AI 输出都
携带可被程序验证的锚点，关键节点由人把关。

## 2. 问题与机会

现有工具的三类失败：

1. **一键生成器**：放任 LLM 自由发挥，虚构量化成果、夸大角色归因
   （把团队成果写成个人主导），求职者投出去的是定时炸弹。
2. **黑盒打分器**：ATS 分是自定义启发式，分数不可解释、不可行动
   （"72 分"之后用户不知道做什么）。
3. **错位的信任设计**：人工确认放在导出前，但错误在更上游的解析
   环节就已注入并无声污染全链路。

机会：国内场景（中文简历、北森/Moka、Boss 直聘链路）没有认真做的
开源产品；"校验判定 × 人工行为"的配对数据是全行业空白。

## 3. 目标用户与核心场景

国内主动求职者（先互联网/技术岗，该人群 JD 文本规范、付费意愿与
工具接受度高）。核心场景：

- 建库：首次导入简历，把散落的经历变成结构化的、校对过的事实源。
- 投递：看到一个 JD，3 分钟内知道"值不值得投、差距在哪、简历该
  怎么改"，改完导出一版 ATS 友好的定制简历。
- 追踪：知道哪版简历投了哪家、结果如何（v1 只记录）。

## 4. 产品原则（与 ard 一一对应）

| 原则 | 出处 |
| --- | --- |
| 所有 AI 输出携带程序可验证的锚点（span/quote/出处 ID/formula） | ard/0001、0003 |
| 人工节点 1 在事实源、节点 2 在导出前；咽喉是前者 | ard/0002 |
| 校验只做举证和判定，不做黑盒打分 | ard/0003 |
| 事实源里没有的就是没有——缺口如实报告，绝不施压改写器 | ard/0004 |
| 默认值站保守一侧：夸大比谦虚危险 | ard/0002、0005 |
| 简历数据不出本机 | ard/0007 |

## 5. 功能范围

### M1：事实源建库与校对（不含任何改写能力）

| # | 用户故事 | 验收标准 |
| --- | --- | --- |
| 1.1 | 我上传 PDF/DOCX 简历，系统解析出结构化事实源 | 每条字段带 source_span，程序 100% 可回查到 canonical_text |
| 1.2 | 我看到左栏原文、右栏字段表，点击字段原文联动高亮 | 高亮位置与 span 一致；双栏简历不乱（乱序时有 MinerU 重解析按钮） |
| 1.3 | 系统标记可疑字段而不是让我逐字核对 | 异象徽标覆盖：日期倒序/重叠、日期格式歧义、百分比超界、金额量级突变、缺字段 |
| 1.4 | 团队/个人归因含糊的条目，系统强制我表态 | team/mixed/unknown 未确认前条目为"待确认"态 |
| 1.5 | 歧义日期我看到"原始 ↔ 归一化"对照再确认 | 确认结果写回结构化字段，canonical_text 不被修改 |
| 1.6 | 没配 API key 我也能体验全流程 | mock 模式可跑通，界面明确标示"演示数据，非真实解析水平" |
| 1.7 | 首次导入我全量过一遍；之后改简历只看有标记的 | 两种模式切换；首次模式无"只看标记"入口 |

### M2：JD 诊断报告

| # | 用户故事 | 验收标准 |
| --- | --- | --- |
| 2.1 | 我粘贴 JD 文本，系统拆出要求清单 | 每条带 must/preferred、关键词；JD 经输入消毒 |
| 2.2 | 每条要求给出简历里的逐字证据，或如实标缺口 | 证据 quote 程序验证为原文子串；quote 全半角/空白差异不误报 |
| 2.3 | 缺口条目告诉我"最接近的经历是什么" | 报告呈现"无直接证据，最接近 X，是否相关？"，我一句话确认可捞回 |
| 2.4 | must 和 preferred 缺口分开看 | 分层呈现；全 must 缺口时直接提示"岗位可能不值得投" |
| 2.5 | 等待过程我看到进行到哪一步 | SSE 分步：解析 JD → 举证中（n/N）→ 生成报告 |

**M2 开工条件**：10–20 份标注测试集（JD-简历对 + 期望举证结果）就绪。

### M3：改写、校验与导出

| # | 用户故事 | 验收标准 |
| --- | --- | --- |
| 3.1 | 系统按诊断结果改写，每句话声明出处 | 输出句→事实源 ID 映射；硬性缺口不在改写目标内 |
| 3.2 | 改写稿过三层校验，不过的分流处理 | L0/L1/L2 + 归因动词检查；可修复 ≤2 轮重试；硬性缺口升级回报告 |
| 3.3 | 数字润色有边界 | "70 万→91 万"写成"提升 30%"合法（带 formula 且重算通过）；编造的数字被 L0 拦下 |
| 3.4 | 团队成果不会被写成我主导的 | attribution=team/mixed/unknown + 主导级动词 = 程序级拦截 |
| 3.5 | 我逐条确认/拒绝/修改每处改动再导出 | diff 视图；出处 ID 可跳原文；硬性缺口不在此标红 |
| 3.6 | 我的每个确认动作都被记录 | gate_events 含动作 + 当次校验判定快照 |
| 3.7 | 导出 PDF 能过 ATS 解析 | 单栏、标准章节名、无表格文本框；v2 再做网申/直聘双模板 |

### 明确不做（v1）

- 招聘网站抓取与自动投递（封号风险 + 平台条款）
- 多人协作、云端同步
- 面试准备、求职信生成（链路完整后再议）
- 事件数据分析（只记录，见 ard/0006）

## 6. 非功能需求

- **隐私**：全部数据本地 SQLite；唯一的出网请求是用户自配的 LLM API；
  设置页可查看端点。
- **安全**：简历与 JD 双向输入消毒（含 PDF 隐形文本清洗）；formula
  白名单求值，无 eval。
- **性能**：M1 解析 ≤1 分钟/份；M2 诊断、M3 改写校验为分钟级，必须
  SSE 分步进度，不允许无反馈加载。
- **可演进**：normalize 版本化（改动=全量重入库，见 ard/0001）；
  embedding 粗排接口预留但不启用。

## 7. 成功指标

| 指标 | 来源 | 目标 |
| --- | --- | --- |
| gate1 字段修正率 | gate_events | 高不等于差（反映抽取质量），用于监测抽取改进 |
| 校验误报率（用户驳回标红句） | gate_events × 判定快照 | 逐版本下降 |
| 校验漏报率（用户手改未标红句） | 同上 | 逐版本下降 |
| 举证准确/缺口误判 | 标注测试集回归 | M2 验收门槛，阈值随测试集定 |
| M1 完成首次校对时长 | 埋点 | 中位数 <15 分钟（几十条字段） |

## 8. 里程碑与依赖

M1（地基，纯技术依赖）→ M2（依赖标注测试集，人工含量高，**M1 开发
期间并行开始攒**）→ M3（依赖 M2 的要求清单契约稳定）。
